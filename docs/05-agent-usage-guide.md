# twit 에이전트용 사용 가이드

- 작성일: 2026-09-09
- 최종 갱신: 2026-09-10. 2차 개선(환경변수 주소록, 명시적 이름 지정, 미리보기, 일괄 읽기)을 반영했다.
- 상태: 구현된 twit v2 CLI 기준. [03-v2-mail-inbox-design.md](./03-v2-mail-inbox-design.md)의 사용 관례를 에이전트가 따를 수 있게 옮긴 안내다.
- 구성: 1장은 에이전트 지침 파일에 그대로 붙여 넣을 수 있는 짧은 절이고, 2장 이하는 사람이 읽는 설명이다.

## 1. 에이전트 지침 (붙여 넣기용)

아래 절을 통째로 복사해 각 에이전트의 지침 파일에 넣는다.

```markdown
## twit 메일함 규칙

- twit은 사람과 CLI 에이전트가 쓰는 로컬 메일함이다. 상대를 깨우지 않으며, 보관은 작업 완료가 아니다.
- `twit contacts --json`으로 주소록을 확인한다. 이 목록은 현재 프로세스가 상속한 환경변수 `TWIT_CONTACTS`에서 온다.
- 자기 이름은 주소록에서 제품명과 맞는 항목을 고른다. 맞는 것이 없거나 둘 이상이면 사람에게 묻는다. 사람이 지정한 이름이 있으면 그것을 쓴다. 임의의 새 이름을 만들지 않는다.
- 수신자 이름은 사람의 지시에 적힌 이름을 그대로 쓴다.
- 조회·읽기·답장·보관은 `--as <이름>`으로 누구의 메일함인지 명시한다.
- 전송은 `twit send --from <이름> --to <이름> --subject "..." --body "..."` 이다.
- 세션을 시작할 때와 작업을 마치기 전에 `twit inbox --as <이름> --json`을 실행한다.
- 기본 인박스는 읽었지만 보관하지 않은 메시지도 포함한다. 처리 도중 새 메시지만 보려면 `--unread`를 쓴다.
- 읽지 않은 메시지는 `twit read <id> --as <이름> --json`으로 읽는다. 여러 건은 `twit read M-001 M-002 --as <이름>`, 모두 읽기는 `twit read --unread --as <이름>`다.
- 필요한 응답은 `twit reply <id> --as <이름> --body "..."`로 보낸다. 제목과 대화 ID는 원문에서 온다.
- 처리가 끝난 메시지는 `twit archive <id> --as <이름>`으로 보관해 인박스를 비운다.
- 긴 대화에서 새 답장 위치를 확인할 때는 `twit thread <id> --no-body --json`을 쓴다. 목록의 미리보기로 어떤 내용인지 구분한다.
- 요청 메시지에는 작업 위치의 절대 경로, 요청 내용, 원하는 답장 형식을 본문에 적는다.
- 결과 메시지에는 변경 요약, 저장소와 전체 커밋 ID, 실행한 검증, 남은 사항을 적는다.
- 세션 마무리 메시지에는 회신 필요 여부를 명시한다. 예: "회신 불필요", "확인 답장 요청".
- 자동화 호출에서 응답 유실이 우려되면 처음부터 `--request-id <키>`를 지정한다. 같은 키와 같은 내용으로 다시 호출하면 같은 메시지가 돌아온다.
```

에이전트별 적용 위치:

- Claude Code: 저장소의 `CLAUDE.md`
- Codex: 저장소의 `AGENTS.md`
- OpenCode: 사용 중인 OpenCode 지침 파일

적용 예시(공통 문단):

> 이 저장소에서 협업 요청은 twit 메일함으로 주고받는다. 세션을 시작하면 `twit contacts --json`으로 주소록을 확인하고 자기 이름을 고른 뒤, `twit inbox --as <이름> --json`으로 메시지를 확인한다. 남은 메시지를 처리하고 보관한 뒤에 새 작업을 시작한다. 응답이 필요한 메시지에는 반드시 `twit reply`로 답장한다.

## 2. 설정과 자기 이름

주소록은 환경변수 `TWIT_CONTACTS` 하나다. 셸 설정에 쉼표로 구분한 이름을 적는다.

```sh
export TWIT_CONTACTS="dane,claude,codex,opencode,grok"
twit contacts --json      # { "contacts": ["dane", "claude", "codex", "opencode", "grok"] }
```

- 환경변수는 **프로세스별로 상속**된다. 이미 실행 중인 세션이나 다른 경로로 시작한 앱에는 자동으로 반영되지 않으므로, 각 에이전트는 자기 실행 환경에서 `twit contacts --json`을 실행해 같은 목록이 나오는지 확인한다. 목록을 바꾼 뒤에도 해당 환경에서 다시 확인한다.
- 참여자 등록 명령은 없다. 주소록 편집은 환경변수 수정이 전부다. 목록에 없는 이름으로 보내거나 `--as`로 조회하면 `NOT_FOUND`(종료 코드 3)로 거절되며 현재 목록이 안내된다.
- 주소록 자체가 설정되어 있지 않으면 모든 명령이 `ACTOR_NOT_CONFIGURED`(종료 코드 8)로 거절되고 설정 예시를 안내한다.
- 에이전트는 `contacts` 목록에서 자기 제품명과 맞는 이름을 고른다. 없거나 둘 이상이면 사람에게 묻는다. 사람이 세션에서 이름을 지정하면 그것을 우선한다. 이름은 역할이나 세션 번호가 아니다.

## 3. 세션 규칙

세션을 시작할 때와 작업을 마치기 전에 `twit inbox --as <이름> --json`을 실행한다.

- 기본 인박스는 **읽었지만 보관하지 않은 메시지도 포함**한다. 이전 세션에서 읽고 처리하지 못한 요청이 함께 보인다.
- 읽지 않은 메시지는 `read`로 읽고, 필요하면 `reply`하고, 처리가 끝난 메시지는 `archive`로 보관해 인박스를 비운다.
- 처리 도중 새로 온 것만 보려면 `--unread`, 한 번에 모두 읽으려면 `twit read --unread --as <이름>`을 쓴다.
- 인박스에 남아 있는 메시지는 아직 처리하지 않은 것으로 간주한다.
- 보관은 인박스 정리 상태일 뿐이다. twit은 보관을 작업 완료나 수락으로 해석하지 않는다.
- 세션 마무리 메시지에는 상대가 답장해야 하는지 여부를 본문에 명시한다. 예: "회신 불필요", "확인 답장 요청".

## 4. 요청 작성

요청·질문·결과를 구별할 필요가 있으면 제목과 본문에 직접 적는다. 요청 본문에는 작업 위치의 절대 경로, 요청 내용, 원하는 답장 형식을 적는다.

```text
작업 위치: /workspace/example
재시도 로직에서 중복 저장을 방지해주세요.
변경 범위는 payment 모듈입니다.
작업 후 변경 요약과 실행한 테스트 결과를 답장해주세요.
```

## 5. 긴 문서·폴더 전달

| 전달 대상 | 권장 방식 |
|---|---|
| 짧은 요청·질문·결과 | 메시지 본문에 직접 작성 |
| 전송 당시 내용을 보존할 작업 명세 | `--body-file`로 파일 내용을 본문에 저장 |
| 매우 긴 문서 | 본문에 절대 경로와 읽을 범위 작성 |
| 여러 문서가 정리된 폴더 | 폴더 절대 경로, 시작 문서, 읽을 순서 또는 범위 작성 |
| 긴 본문이 있는 대화에서 새 답장 확인 | `thread --no-body`로 위치를 확인한 뒤 필요한 메시지만 `read` |

폴더 전달 예시:

```text
아래 명세에 따라 구현해주세요.

문서 폴더: /path/to/project/docs
시작 문서: /path/to/project/docs/README.md
읽을 범위: README에서 안내한 결제 재시도 관련 명세와 검증 시나리오

README에 안내된 순서로 필요한 문서를 읽어주세요.
작업 후 변경 요약과 검증 결과를 답장해주세요.
```

저장과 참조의 시점 차이:

- `--body-file specification.md`는 파일 **내용 자체**를 전송 시점에 저장한다. 나중에 원본 파일이 바뀌어도 전송한 메시지는 바뀌지 않는다.
- 본문에 적은 경로는 문자열로 보관되며, **수신자가 읽는 시점의 파일**을 가리킨다. 전송 시점의 내용이 필요하면 `--body-file`로 저장하거나 커밋 ID를 함께 적는다.
- 커밋 지정만으로 현재 작업 파일이 해당 버전으로 고정되지는 않는다. 필요하면 별도 사본의 절대 경로를 전달한다.
- twit은 참조 파일을 읽거나 검사하지 않는다. 파일이 없거나 접근할 수 없으면 수신자가 답장으로 알린다.

## 6. 긴 대화 확인

대화가 길어지면 본문을 모두 읽는 대신 요약 목록으로 새 답장을 찾는다.

```sh
twit thread M-001 --no-body --as codex --json
twit read M-004 --as codex --json
```

`--no-body`의 각 항목은 ID, 발신자 → 수신자, 시각, 답장 대상, 읽음 표시, 본문 길이와 들여쓴 미리보기를 담는다. 미리보기는 본문의 공백이 아닌 첫 줄(최대 80자)이다. 필요한 메시지만 골라 `read`하면 본문을 읽을 때 쓰는 토큰을 아낀다. 대화 조회는 읽음·보관 상태를 바꾸지 않는다.

여러 건을 한 번에 읽으면 본문이 그만큼 출력된다. 긴 본문이 예상되면 목록의 미리보기나 `thread --no-body`로 먼저 확인하고 필요한 ID만 지정한다.

## 7. 결과 답장

작업을 마치면 결과를 답장으로 보낸다. 변경 요약, 저장소와 커밋, 실행한 검증, 남은 사항을 적는다.

```text
중복 저장 방지 로직을 추가했습니다.
저장소: /workspace/example
커밋: <전체 커밋 ID>
검증: 관련 테스트 8개 통과
남은 사항: 외부 API 연동 검증은 실행하지 않았습니다.
```

## 8. 중복 방지

응답 유실이 우려되는 자동화 호출에서는 처음부터 `--request-id <키>`를 지정한다.

- 같은 발신자가 같은 키와 같은 내용으로 다시 호출하면 기존 메시지 ID가 `replayed: true`로 돌아온다. 새 메시지는 만들어지지 않는다.
- 같은 키에 다른 내용을 넣으면 `REQUEST_ID_CONFLICT`(종료 코드 5)로 거절된다.
- 키를 생략한 전송·답장은 호출할 때마다 새 메시지다.

## 9. 한계

- 전송은 수신함에 저장하는 동작일 뿐, 수신자의 프로세스나 모델을 깨우지 않는다. 각 참여자는 스스로 조회해야 한다.
- 같은 이름을 여러 세션이 쓰면 요청을 중복 수행할 수 있다. 세션을 구분하려면 서로 다른 이름을 사용한다.
- 메시지 본문과 발신·수신 정보는 전송 후 수정·삭제할 수 없다. 잘못 보낸 내용은 후속 메시지로 정정한다.

## 10. 수동 연동 검증 기록

실제 서로 다른 두 CLI 에이전트의 요청 → 질문 → 답변 → 결과 전달 검증을 아래에 기록한다.

- 1차 검증(2026-09-09, Claude Code `claude-1` ↔ OpenCode `opencode-1`, 등록제): 리뷰 요청 전송 → 리뷰 회신 → 수정 요청 반영 → 재검증 회신. 두 차례의 메시지 왕복에서 각 에이전트가 `inbox --json`으로 세션을 시작하고, `read`로 읽고, `reply`로 답장하고, `archive`로 보관해 인박스를 비웠다. 이 과정에서 나온 첫 사용자 피드백이 07 문서와 2차 개선(커밋 194bb69)으로 이어졌다.
- 2차 검증(2026-09-10, `claude` ↔ `codex`, 환경변수 주소록): 2차 개선 설계 계획 공유(M-006) → 설계 검토 답장(M-007) → 검토 재검토와 스킬 교체안 회신(M-008) → opencode에 구현 요청(M-009). 코드가 아닌 설계 문서의 왕복이었으나 이름 지정·세션 규칙·회신 불필요 명시 관례가 그대로 검증됐다.
- 3차 검증(2026-09-10~11, `claude` ↔ `opencode`): 구현 요청(M-009, v1 CLI로 전송) → 구현 완료 보고(M-010, v2 CLI로 답장) → `claude`가 v2 CLI(`twit inbox --as claude`, `twit read M-010 --as claude`, `twit archive M-010 --as claude`)로 읽고 검증한 뒤 보관. 한 대화 안에서 v1 전송과 v2 답장·읽기가 이어졌고, 미리보기가 인박스 목록에 표시됐다.
