# twit v2 첫 사용 후기와 2차 개선 목표

- 작성일: 2026-09-10
- 상태: 2차 개선 계획. 시범 사용에서 나온 후기를 정리하고, 사용자의 결정을 반영해 개선 범위를 확정한다.
- 관계: 시범 사용 기록은 [05-agent-usage-guide.md](./05-agent-usage-guide.md) 10장, 구현 상태는 [06-implementation-log.md](./06-implementation-log.md)를 따른다. 여기서 확정한 변경은 03·04 문서를 먼저 고친 뒤 구현한다.

## 1. 시범 사용 개요

2026-09-09에 Claude Code(`claude-1`)와 OpenCode(`opencode-1`)가 실제 메일함 `~/.twit`에서 한 대화(M-001부터 M-005)로 두 차례 왕복했다. 내용은 구현 커밋에 대한 리뷰 전달, 수정 결과 회신, 첫 사용자 질문, 답변과 반영이었다. 각 세션의 조회는 사람이 지시했고 twit은 어느 쪽도 실행하지 않았다.

이 문서의 후기는 `claude-1` 쪽에서 실제로 명령을 호출한 에이전트의 관점이다.

## 2. 사용 후기

### 2.1 잘 맞았던 점

- 명령이 의도와 1:1로 대응해 무엇을 호출할지 고민이 없었다. `inbox`, `read`, `reply` 세 개로 왕복이 끝났다.
- `thread --no-body`를 매번 사용했다. 읽지 않은 메시지 위치와 답장 체인을 한 화면에서 파악하고 필요한 한 건만 읽었다. 긴 리뷰 본문이 다시 출력되지 않아 문맥 사용량이 줄었다.
- JSON 봉투와 종료 코드가 예측 가능해 결과를 한 줄로 파싱하고 분기할 수 있었다.
- `--request-id`는 재시도할 일이 없었지만 붙여 두는 것만으로 중복 전송 걱정이 사라졌다.
- 오류 메시지가 다음 행동을 알려 줬다. 빈 메일함의 종료 코드 8을 보고 등록으로 바로 넘어갔다.

### 2.2 불편했던 점

| 번호 | 내용 | 처리 |
|---|---|---|
| 1 | 답장이 왔는지 twit으로 알 수 없어 사람이 알려 줘야 조회했다 | 유지. 3장 참조 |
| 2 | 대화 안의 메시지가 모두 같은 제목이라 목록만으로는 어떤 내용의 답장인지 구분이 안 됐다 | 2차 개선 대상 |

## 3. 유지·제외 결정

시범 사용 뒤 사용자가 내린 결정이다. 2차 개선에서 다루지 않는다.

| 항목 | 결정 | 이유 |
|---|---|---|
| 답장 대기와 조회 시점 | 사람이 각 세션에 조회를 지시하는 현재 방식을 유지한다. 세션 훅 등 자동 조회를 두지 않는다 | 사람의 개입은 프로세스에 의도적으로 넣은 부분이다 |
| 역할 별칭(`--to @reviewer` 등) | 두지 않는다 | 역할은 남은 사용량을 보고 사람이 그때그때 정한다. 같은 모델이 문맥만 다른 상태로 다른 역할을 맡을 수도 있어 참여자와 역할을 고정할 수 없다 |
| 환경변수 역할 지정(`TWIT_REVIEWER` 등) | 두지 않는다 | 위와 같은 이유. 역할 이름을 환경에 고정하는 것도 같은 문제를 만든다 |
| 프로젝트별 주소록 | 두지 않는다. 참여자는 전역 `~/.twit`으로 관리한다 | 우선 전역으로 운영해 본다 |

따라서 수신자 지정은 다음 관례로 정리한다.

- 수신자는 사람이 세션 지시에서 참여자 ID로 알려 준다. 예: "리뷰 결과를 `opencode-1`에게 보내라".
- 에이전트는 `twit contacts`로 ID를 확인하고 그대로 `--to`에 쓴다. 역할이나 별칭으로 추정하지 않는다.
- 참여자의 표시 이름에 CLI와 모델을 적어 두면 사람이 지시할 때 구분하기 쉽다. 예: `Claude Code (Fable 5.1)`. 이는 등록 관례이며 새 필드는 두지 않는다.

## 4. 2차 개선 목표

### 목표 1: 목록에 본문 첫 줄 미리보기

불편 2에 대응한다. `inbox`, `sent`, `thread --no-body`의 각 항목에 본문 첫 줄을 미리보기로 붙인다.

- 미리보기는 본문에서 공백이 아닌 첫 줄을 골라 앞뒤 공백을 제거한 것이다. 80자를 넘으면 80자에서 자르고 `…`를 붙인다.
- JSON에는 `preview` 필드로 넣는다. 본문은 여전히 목록에 포함하지 않는다.
- 텍스트 목록은 제목 뒤에 새 열로 붙이지 않고, 각 항목 아래에 들여쓴 줄로 표시한다. 한 항목이 두 줄이 되지만 제목 열의 잘림을 피한다.
- 03 문서의 "자르거나 요약하지 않는다"는 `--no-body`의 본문 길이 규칙이다. 미리보기는 본문이 아니라 목록 필드이므로 충돌하지 않지만, 03 문서 5.1과 5.5에 미리보기의 정의와 한계를 명시해 둔다.
- Markdown 제목 기호(`#`)로 시작하는 첫 줄은 그대로 둔다. 해석하지 않는다.

검증: 첫 줄이 빈 줄인 본문, 80자를 넘는 첫 줄, 한 줄뿐인 본문에서 미리보기가 규칙대로 나오고 `body_length`는 그대로인지 확인한다.

### 목표 2: 읽지 않은 메시지 일괄 읽기

불편 3에 대응한다. `read`가 여러 ID를 받고, `--unread` 옵션으로 기본 인박스의 읽지 않은 메시지를 한 번에 읽는다.

```sh
twit read M-004 M-005
twit read --unread
twit read --unread --json
```

- 여러 ID는 지정한 순서대로, `--unread`는 오래된 순서(`seq` 오름차순)로 반환한다. 대화 흐름을 따라 읽기 위해서다.
- 각 메시지에 `marked_read`를 개별로 붙인다. JSON은 `{ "messages": [ Message + marked_read ] }`다.
- 권한 검사는 메시지마다 한다. 여러 ID 중 하나라도 없거나 권한이 없으면 아무것도 읽음 처리하지 않고 오류를 낸다. 부분 성공을 두지 않는다.
- `--unread`는 ID와 함께 쓸 수 없다. 보관된 메시지는 포함하지 않는다.
- `--unread` 결과가 비어 있으면 빈 목록으로 정상 종료한다.
- 한 번에 여러 본문이 출력되므로 문맥 사용량이 커질 수 있다. 05 가이드에 "긴 본문이 예상되면 `inbox` 미리보기나 `thread --no-body`로 먼저 확인한 뒤 필요한 ID만 지정한다"를 적는다.

검증: 읽지 않은 메시지 세 건 중 두 건을 ID로 읽으면 나머지 한 건은 그대로인지, `--unread`가 보관된 미읽음 메시지를 건드리지 않는지, 권한 없는 ID가 섞이면 전부 미변경인지 확인한다.

### 목표 3: 수신자 지정 관례를 가이드에 반영

3장의 관례를 05 가이드 1장 지침과 2장 설정에 적는다. 코드 변경은 없다.

- 1장 지침에 "수신자는 사람의 지시에 적힌 참여자 ID를 쓴다. 역할이나 이름으로 추정하지 않는다"를 추가한다.
- 2장에 표시 이름 관례와 등록 예시를 적는다.

### 목표 4: 시범 사용에서 검증된 관례를 가이드에 고정

- 세션 마무리 시 상대에게 회신이 필요한지 여부를 본문에 명시한다. 예: "회신 불필요", "확인 답장 요청". 읽음 여부를 노출하지 않는 대신 본문으로 기대를 밝히는 관례다.
- 처리한 메시지는 보관해 인박스를 비운다는 규칙이 두 에이전트 모두에서 동작했음을 10장 기록으로 확인했으므로 1장 지침을 유지한다.
