# twit v2 — 메일 인박스 기능 설계

- 작성일: 2026-09-09
- 상태: 기능 설계. 1차 구현과 두 에이전트 연동 검증을 마쳤다. 2026-09-10에 2차 개선(4장 참여자 식별의 환경변수 주소록 전환, 5장 미리보기·일괄 읽기)을 반영했고 같은 날 구현을 마쳤다(커밋 0f2d03d~f802d29). 배경은 [07-first-use-review.md](./07-first-use-review.md)에 있다.
- 범위: 단일 머신에서 사람과 CLI 에이전트가 사용하는 비동기 메시지 인박스
- 관계: 01·02 문서의 작업 관리 모델을 대체한다. 이전 명세는 v2에 자동 적용하지 않는다.

## 1. 목적

twit은 에이전트가 서로 메시지를 남기고 필요할 때 직접 읽는 메일 인박스다. 요청, 질문, 답변, 결과, 검토 의견을 일반 메시지로 주고받는다.

twit은 내용을 보관하고 연결할 뿐, 내용을 해석하거나 작업 진행을 판단하지 않는다. 일반 이메일 서버와 연결하는 기능도 초기 범위에 포함하지 않는다.

### 기본 원칙

1. 에이전트 또는 사람이 명시적으로 CLI를 호출한다.
2. 폴링, 예약 조회, 알림 구독, 자동 실행·재개·재시도는 없다.
3. 전송은 수신함에 저장하는 동작이다. 수신자의 실행이나 확인을 보장하지 않는다.
4. 에이전트 간 협업 내용은 twit 메시지와 답장으로 전달한다.
5. twit은 작업 상태, 담당자 인수, 실행 시도, 제출 승인 규칙을 관리하지 않는다.
6. 읽음·보관은 수신함 정리 상태다. 요청 수락이나 작업 완료를 의미하지 않는다.

### 저장 및 접근 구성

**SQLite에 저장하고 CLI로 사용하는 로컬 에이전트 메일함**으로 구성한다.

```text
사람 또는 에이전트 → twit CLI → SQLite
```

- 메시지 본문은 SQLite의 `TEXT`로 저장한다. 긴 Markdown 작업 명세도 본문으로 전달할 수 있다.
- 대화 ID와 답장 대상 ID로 메시지를 연결하고, 메시지와 수신 상태를 트랜잭션으로 함께 저장한다.
- CLI의 메시지 처리 계층에서 호출자와 발신자·수신자를 확인한다. 이는 DB 파일에 직접 접근할 수 있는 로컬 사용자를 차단하는 보안 경계는 아니다.
- 모든 명령은 공통 JSON 출력 계약을 따른다.
- 파일 이동으로 읽음·보관 상태를 표현하지 않는다. 별도 서버나 실행기는 두지 않는다.

## 2. 사용 흐름

```text
Codex: 구현 요청 전송
  → OpenCode: 인박스 조회 → 메시지 읽기 → 질문 답장
  → Codex: 인박스 조회 → 질문 읽기 → 답변
  → OpenCode: 답변 읽기 → 작업 수행 → 결과 답장
  → Codex: 결과 읽기 → 확인 또는 추가 요청 답장
```

각 화살표 사이에 대기 시간이 있을 수 있다. 다음 참여자는 스스로 조회해야 하며, twit이 실행하지 않는다.

## 3. 최소 개념

| 개념 | 의미 |
|---|---|
| 참여자 | 사람 또는 에이전트를 구분하는 고유 ID |
| 메시지 | 발신자 한 명이 수신자 한 명에게 보내는 제목·본문 |
| 답장 | 기존 메시지를 가리키는 새 메시지 |
| 대화 | 최초 메시지와 그에 연결된 답장 묶음 |
| 인박스 | 자신이 받은 메시지 중 보관하지 않은 메시지 목록 |
| 보낸함 | 자신이 보낸 메시지 목록 |

초기에는 메시지 하나당 수신자 한 명만 지원한다. 참조·숨은 참조·그룹·전체 회신은 제외한다. 다른 참여자에게 전달하려면 새 메시지를 보내고 필요한 내용을 직접 적는다.

## 4. 참여자와 자기 이름

```sh
export TWIT_CONTACTS="dane,claude,codex,opencode,grok"   # 셸 설정에 한 번
twit contacts
twit inbox --as claude
twit send --from claude --to codex --subject "..." --body-file request.md
```

- 주소록은 환경변수 `TWIT_CONTACTS`에 쉼표로 구분한 이름 목록이다. 셸 설정에 적어 두면 그 셸에서 시작한 프로세스가 상속한다. 환경변수는 프로세스별로 상속되므로 이미 실행 중인 세션이나 다른 경로로 시작한 앱에는 자동으로 반영되지 않는다. 각 에이전트는 자기 실행 환경에서 `twit contacts --json`을 실행해 같은 목록이 나오는지 확인하고, 목록을 바꾼 뒤에는 해당 환경에서 다시 확인한다. 이름은 사람이 정한 단순한 발신·수신 이름이며 역할이나 세션 번호가 아니다.
- 참여자 등록 명령과 참여자 저장 테이블은 두지 않는다. 주소록 편집은 환경변수 수정이 전부다. 표시 이름, 종류, 역할 같은 부가 정보도 두지 않는다.
- `contacts`는 이 목록을 그대로 보여 준다.
- 전송은 `--from`과 `--to`로 발신자와 수신자를 명시한다. 인박스·읽기·답장·대화·보낸함·보관은 `--as`로 누구의 것인지 명시한다. 자기 이름을 환경변수로 미리 정해 두는 방식은 두지 않는다.
- 에이전트는 자기 이름을 스스로 고른다. `contacts`를 실행해 자기 제품명과 맞는 항목을 찾고, 맞는 것이 없거나 둘 이상이면 사람에게 묻는다. 사람이 세션에서 이름을 지정하면 그것을 우선한다. 목록은 많아야 네댓 개이므로 이 판단은 에이전트가 한다.
- `--as`, `--from`, `--to`의 이름이 목록에 없으면 오류로 거절하고 현재 목록을 보여 준다. 오타로 새 인박스를 만들지 않는다. 등록 절차가 아니라 사람이 적어 둔 목록과 대조하는 것이다.
- 주소록이 설정되지 않았거나 비어 있으면 모든 명령을 오류로 거절하고 설정 방법을 안내한다.
- 목록에서 이름을 지우면 그 이름으로 새 메시지를 보내거나 받을 수 없다. 과거 메시지는 남으며, 다시 보려면 이름을 목록에 넣는다.
- 초기 버전은 신뢰된 로컬 사용 환경을 전제로 한다. 이름 지정은 보안 인증 수단이 아니다.
- CLI는 `--as`로 지정한 이름에게 오거나 그 이름이 보낸 메시지만 조회·답장하게 한다. 보관 상태는 수신자만 변경한다.

## 5. 기능과 명령

모든 명령은 에이전트가 파싱할 수 있는 `--json` 출력을 지원한다. `send` 외의 명령은 `--as <이름>`으로 누구의 메일함인지 지정한다. 아래 예시에서는 `--as`를 생략했다.

### 5.1 인박스 조회

```sh
twit inbox
twit inbox --unread
twit inbox --archived
twit inbox --all
```

- 기본값: 자신에게 온 보관되지 않은 메시지 전체. 읽은 메시지도 포함한다.
- `--unread`: 기본 인박스 중 읽지 않은 메시지만 반환한다.
- `--archived`: 보관한 메시지만 반환한다.
- `--all`: 보관 여부와 관계없이 받은 메시지 전체를 반환한다.
- 초기에는 이 세 필터를 동시에 사용하면 입력 오류로 처리한다.
- 목록은 최신 메시지순으로 정렬하며 같은 시각이면 내부 생성 순서로 정렬한다.
- 출력: 메시지 ID, 읽음 여부, 발신자, 제목, 수신 시각, 본문 미리보기. `--all`에서는 보관 여부도 표시한다.
- 미리보기는 본문에서 공백이 아닌 첫 줄을 골라 앞뒤 공백을 제거한 것이다. 80자(코드 포인트)를 넘으면 80자에서 자르고 `…`를 붙인다. Markdown 기호는 해석하지 않고 그대로 둔다. 미리보기는 목록에서 어떤 내용의 메시지인지 구분하기 위한 필드이며 본문을 대신하지 않는다.
- 본문은 목록에 포함하지 않는다. 조회만으로 읽음·보관 상태가 바뀌지 않는다.
- 빈 목록은 정상 결과다. 초기에는 페이지 제한 없이 전체 목록을 반환한다.

### 5.2 메시지 읽기

```sh
twit read M-001
twit read M-004 M-005
twit read --unread
```

- 각 메시지의 ID, 발신자, 수신자, 제목, 본문, 전송 시각, 답장 대상 ID, 대화 ID를 표시한다.
- 수신자가 읽으면 해당 메시지만 읽음으로 표시한다. 이미 읽었다면 같은 상태를 유지한다.
- 발신자가 보낸 메시지를 읽어도 수신자의 읽음 상태를 변경하지 않는다.
- 읽기는 보관을 해제하지 않으며, 지정하지 않은 다른 메시지를 읽음 처리하지 않는다.
- 읽음은 CLI가 메시지를 조회했다는 뜻이다. 모델의 이해나 수락을 증명하지 않는다.
- ID를 여러 개 지정하면 지정한 순서대로 반환한다. 같은 ID를 두 번 지정하면 입력 오류다.
- `--unread`는 기본 인박스(보관하지 않은 메시지)의 읽지 않은 메시지를 오래된 순서로 모두 읽는다. 보관된 메시지는 포함하지 않는다. ID와 함께 쓸 수 없다. 결과가 없으면 빈 목록으로 정상 종료한다.
- 여러 건을 읽을 때 하나라도 없거나 권한이 없으면 어느 것도 읽음 처리하지 않고 오류를 낸다. 부분 성공은 없다.
- 여러 건을 한 번에 읽으면 본문이 그만큼 출력된다. 긴 본문이 예상되면 목록의 미리보기나 `thread --no-body`로 먼저 확인하고 필요한 ID만 지정한다.

### 5.3 메시지 보내기

```sh
twit send --from codex --to opencode --subject "재시도 로직 구현 요청" --body-file request.md
twit send --from opencode --to codex --subject "참고 사항" --body "검증 환경은 로컬입니다."
```

- 발신자, 수신자, 제목, 본문은 필수이며 공백만 있는 값은 거절한다. 발신자와 수신자는 주소록에 있는 이름이어야 한다.
- `--body`와 `--body-file` 중 하나만 지정한다. `--body-file -`은 표준 입력을 읽는다.
- 파일 입력은 호출 시 본문으로 저장한다. 나중에 파일이 바뀌어도 전송한 메시지는 바뀌지 않는다.
- 전송 시 새 메시지 ID와 대화 ID를 발급한다. 수신자에게는 읽지 않음·미보관으로 나타난다.
- 성공 응답은 저장 완료를 의미한다. 수신 확인이나 작업 착수를 의미하지 않는다.
- 자신에게 보내기도 허용한다. 이 경우 보낸함과 인박스에 같은 메시지가 나타난다.

### 5.4 답장

```sh
twit reply M-001 --body-file answer.md
```

- `--as` 이름이 원문의 수신자면 원래 발신자에게 보낸다.
- `--as` 이름이 원문의 발신자면 원래 수신자에게 후속 메시지를 보낸다.
- 답장은 같은 대화 ID와 직접 답장한 메시지 ID를 가진 새 메시지다.
- 제목은 원문 제목을 유지한다. `Re:`를 반복해서 추가하지 않는다.
- 본문 입력 규칙은 전송과 같다. 원문 전체를 자동 인용하지 않는다.
- 보관된 메시지에도 답장할 수 있다. 원문 보관 상태는 유지한다.
- 새 답장은 상대방 인박스에 읽지 않음·미보관으로 들어간다. 이전 메시지를 보관했어도 새 답장은 숨겨지지 않는다.
- 답장 자체는 원문을 읽음 또는 보관 처리하지 않는다.

### 5.5 대화 조회

```sh
twit thread M-001
twit thread M-001 --no-body
```

- 메시지 하나의 ID로 같은 대화에 속한 메시지 전체를 오래된 순서대로 표시한다.
- 각 메시지의 ID, 발신자·수신자, 시각, 답장 대상, 본문을 표시한다. 자신이 받은 메시지에는 읽음 여부를 함께 표시한다.
- `--no-body`: 본문을 생략하고 각 메시지의 ID, 발신자·수신자, 시각, 답장 대상, 읽음 여부, 본문 길이(문자 수), 5.1과 같은 규칙의 미리보기만 표시한다. 긴 명세가 포함된 대화에서 새 답장의 위치를 확인한 뒤 필요한 메시지만 `read`로 읽기 위한 옵션이다. 본문을 자르거나 요약하지 않는다.
- 대화에는 최초 메시지의 두 참여자만 참여한다. 답장에서 수신자를 변경할 수 없다.
- 대화 조회는 옵션과 관계없이 읽음·보관 상태를 변경하지 않는다. 새 메시지 확인 표시는 개별 `read`로 수행한다.
- 자동 요약, 원시 로그 수집, 관련 파일 열기는 하지 않는다.

### 5.6 보낸함 조회

```sh
twit sent
```

- 자신이 보낸 메시지를 최신순으로 표시한다.
- 출력: 메시지 ID, 수신자, 제목, 전송 시각, 5.1과 같은 규칙의 미리보기.
- 상대방의 읽음·보관 여부를 전달 확인 기능으로 노출하지 않는다.
- 본문과 답장은 `read` 또는 `thread`로 확인한다.

### 5.7 보관과 복원

```sh
twit archive M-001
twit unarchive M-001
```

- 수신자만 자신이 받은 메시지를 보관·복원할 수 있다.
- 보관은 기본 인박스에서 숨기는 동작이며 삭제가 아니다.
- 읽지 않은 메시지도 보관할 수 있다. 읽음 여부는 유지한다.
- 복원하면 기본 인박스에 다시 나타나고 기존 읽음 여부를 유지한다.
- 같은 명령을 반복해도 동일한 최종 상태로 성공한다.
- 한 메시지에만 적용하며 대화 전체를 보관하지 않는다.

## 6. 본문과 산출물

메시지 유형, 작업 템플릿, 완료 조건 필드를 강제하지 않는다. 요청·질문·결과를 구별할 필요가 있으면 제목과 본문에 적는다.

요청 예시:

```text
작업 위치: /workspace/example
재시도 로직에서 중복 저장을 방지해주세요.
변경 범위는 payment 모듈입니다.
작업 후 변경 요약과 실행한 테스트 결과를 답장해주세요.
```

결과 예시:

```text
중복 저장 방지 로직을 추가했습니다.
저장소: /workspace/example
커밋: <전체 커밋 ID>
검증: 관련 테스트 8개 통과
남은 사항: 외부 API 연동 검증은 실행하지 않았습니다.
```

파일 첨부·업로드는 제공하지 않는다. 파일은 절대 경로, 커밋은 저장소 위치와 함께 본문에 적는 것을 권장한다. twit은 참조 파일을 읽거나 존재 여부를 검사하지 않는다.

### 긴 문서와 문서 폴더 전달 가이드

저장 가능 여부와 별개로, 매우 긴 본문을 매번 읽으면 에이전트의 문맥을 많이 사용한다. CLI 도움말과 에이전트용 사용 가이드에는 다음 기준을 안내한다. 크기에 따른 자동 변환이나 강제 제한은 두지 않는다.

| 전달 대상 | 권장 방식 |
|---|---|
| 짧은 요청·질문·결과 | 메시지 본문에 직접 작성 |
| 전송 당시 내용을 보존할 작업 명세 | `--body-file`로 파일 내용을 본문에 저장 |
| 매우 긴 문서 | 본문에 절대 경로와 읽을 범위 작성 |
| 여러 문서가 정리된 폴더 | 폴더 절대 경로, 시작 문서, 읽을 순서 또는 범위 작성 |
| 긴 본문이 있는 대화에서 새 답장 확인 | `thread --no-body`로 위치를 확인한 뒤 필요한 메시지만 `read` |

폴더 전달 예시:

```text
아래 명세에 따라 구현해주세요.

문서 폴더: /path/to/project/docs
시작 문서: /path/to/project/docs/README.md
읽을 범위: README에서 안내한 결제 재시도 관련 명세와 검증 시나리오

README에 안내된 순서로 필요한 문서를 읽어주세요.
작업 후 변경 요약과 검증 결과를 답장해주세요.
```

- 수신 에이전트가 자신의 파일 도구와 권한으로 경로를 읽는다. 메시지 수신이 파일 접근 권한을 확대하지 않는다.
- twit은 본문에 적힌 경로를 문자열로 보관하며 파일·폴더를 복사하거나 내용을 자동으로 펼치지 않는다.
- `--body-file specification.md`는 파일 내용 자체를 저장한다. 경로만 전달하려면 짧은 메시지 본문에 해당 경로를 적는다.
- 본문에 저장한 내용은 전송 시점에 고정되지만, 경로는 수신자가 읽는 시점의 파일을 가리킨다.
- 특정 버전이 필요하면 저장소 경로와 전체 커밋 ID, 커밋 내 문서 경로를 함께 적거나 별도 사본의 절대 경로를 전달한다. 커밋 지정만으로 현재 작업 파일이 해당 버전으로 고정되지는 않는다.
- 파일이 없거나 접근할 수 없으면 수신자가 답장으로 알린다. twit이 경로를 추측하거나 대체 문서를 선택하지 않는다.

이 가이드는 자유 형식 본문 사용법이다. 첨부 개체, 폴더 등록 기능, 문서 수집 기능을 추가하지 않는다.

## 7. 최소 데이터와 처리 규칙

### 저장할 정보

| 대상 | 필드 |
|---|---|
| 메시지 | ID, 대화 ID, 답장 대상 ID(선택), 발신자, 수신자, 제목, 본문, 생성 시각 |
| 수신 상태 | 메시지 ID, 읽은 시각(선택), 보관 여부 |

발신자와 수신자는 주소록의 이름을 문자열로 저장한다. 참여자 테이블은 두지 않으며 주소록은 환경변수에만 있다. 메시지 본문과 발신·수신 정보는 전송 후 수정·삭제하지 않는다. 잘못 보낸 내용은 후속 메시지로 정정한다. 별도 작업·시도·제출·검토·상태 전환 테이블은 두지 않는다.

### 저장과 재호출

- 메시지와 초기 수신 상태는 한 번의 원자적 저장으로 생성한다.
- 선택적인 전송 중복 방지 기록도 해당 메시지와 같은 SQLite 트랜잭션에서 저장한다.
- 메시지는 CLI 종료 이후에도 남아야 한다.
- 전송·답장에는 선택적인 `--request-id`를 제공한다. 같은 발신자가 같은 키와 같은 대상·본문·제목으로 다시 호출하면 기존 메시지 ID를 반환한다. 같은 키에 다른 내용을 넣으면 오류다.
- 요청 키를 생략한 전송·답장은 호출할 때마다 새 메시지다. 응답 유실 후 중복이 우려되면 처음부터 같은 요청 키를 사용한다.
- 자동 재전송은 하지 않는다. 리비전 옵션이나 인수 토큰은 요구하지 않는다.
- 읽음 표시와 보관 변경은 서로의 필드를 덮어쓰지 않는다. 보관·복원이 동시에 요청되면 마지막으로 저장된 동작을 적용한다.

### 출력과 오류

- 기본 출력은 사람이 읽는 텍스트, `--json`은 구조화된 결과다.
- 공통 JSON 필드는 `schema_version`, `ok`, `data`, `error`다. 성공 시 `error`는 `null`, 실패 시 `data`는 `null`이며 `error`에 코드와 메시지를 담는다. 명령별 `data` 필드는 구현 설계에서 정한다.
- 성공은 종료 코드 0, 실패는 비영 종료 코드다.
- 최소 오류 구분: 주소록 미설정 또는 자기 이름 미지정, 주소록에 없는 이름, 메시지 없음, 권한 없음, 잘못된 입력, 요청 키 충돌, 저장 실패.
- JSON 성공·오류는 표준 출력으로, 추가 진단은 표준 오류로 분리한다.
- 오류 시 메시지나 수신 상태가 일부만 저장되지 않게 한다.

## 8. 기존 설계에서 제거하는 것

| 기존 개념 | v2 처리 |
|---|---|
| 작업 카드·담당자·검토자 | 수신자와 자유 형식 본문 |
| 상태 전환·완료 조건 검증 | 참여자가 메시지 내용을 보고 판단 |
| 작업 인수·시도 ID·소유권 | 제공하지 않음 |
| 질문·답변 전용 개체 | 메시지와 답장 |
| 제출·승인 전용 명령 | 결과·검토 의견을 답장 |
| 내용 버전·리비전 충돌 | 전송한 메시지 불변, 후속 메시지로 정정 |
| 이벤트·실행기 | 제공하지 않음 |
| 산출물 테이블·로그 수집 | 본문의 파일·커밋 참조 |

같은 인박스를 여러 세션이 사용하면 동일 요청을 중복 수행할 수 있다. v2는 작업 인수를 관리하지 않으므로 이를 막지 않는다. 별도 참여자 ID를 사용하거나 메시지로 수행 의사를 알리는 것은 참여자의 협업 방식이다.

## 9. 초기 구현 범위

포함:

- 환경변수 주소록 `TWIT_CONTACTS`, `contacts`, `--as`·`--from`·`--to` 이름 지정
- `inbox`, `read`, `send`, `reply`, `thread`, `sent`
- 목록의 본문 미리보기, `read`의 여러 ID·`--unread` 일괄 읽기
- `thread`의 본문 생략 옵션 `--no-body`
- 메시지별 `archive`, `unarchive`
- 영속 저장, 텍스트·JSON 출력, 선택적인 전송 중복 방지 키

제외:

- 폴링·알림·자동 실행·자동 응답
- 작업 추적, 우선순위, 기한, 라벨, 워크플로우
- 복수 수신자, 전달 명령, 외부 이메일 연동
- 검색, 첨부 파일, 메시지 수정·삭제
- 웹 UI, 원격 서버, 여러 머신 지원

SQLite + CLI 구성은 유지한다. 구현 설계에서는 언어·SQLite 드라이버·저장 경로·주소록 해석 규칙·명령별 JSON 데이터 구조를 정한다. 02 문서의 기술을 재사용하더라도 작업 관리 스키마와 서비스 계층을 그대로 가져오지 않는다.

## 10. 검증 및 완료 조건

- [x] A가 보낸 메시지가 B의 인박스에 읽지 않음으로 나타난다.
- [x] 기본 인박스에 읽은 메시지도 표시되고 보관 메시지는 제외된다.
- [x] 인박스 조회와 대화 조회만으로 읽음 상태가 바뀌지 않는다.
- [x] `thread --no-body`가 본문 없이 메시지 목록과 본문 길이를 반환하고 읽음 상태를 바꾸지 않는다.
- [x] 수신자가 `read`하면 해당 메시지만 읽음 처리된다.
- [x] 받은 메시지와 보낸 메시지에 대한 답장이 각각 올바른 상대에게 전송된다.
- [x] 여러 답장이 같은 대화에 연결되고 직접 답장한 메시지도 구분된다.
- [x] 보관한 대화에 새 답장이 오면 새 메시지가 기본 인박스에 나타난다.
- [x] 보관·복원이 읽음 상태와 원문을 바꾸지 않는다.
- [x] 제삼자가 다른 참여자 사이의 메시지를 CLI로 읽거나 답장할 수 없다.
- [x] 주소록에 없는 이름을 `--as`, `--from`, `--to`에 쓰면 거절되고 현재 목록이 안내된다. 주소록 미설정 시 설정 방법이 안내된다.
- [x] 주소록만으로 동작하며 참여자 등록 명령 없이 첫 전송이 된다. 이전 버전의 메시지가 마이그레이션 후에도 조회된다.
- [x] `inbox`, `sent`, `thread --no-body`의 미리보기가 첫 유효 줄·80자 규칙대로 나오고 본문 길이와 원문은 그대로다.
- [x] `read`에 ID 여러 개를 주면 지정 순서대로 읽고, 지정하지 않은 메시지는 그대로다.
- [x] `read --unread`가 보관되지 않은 읽지 않은 메시지만 오래된 순서로 읽고, 보관된 미읽음 메시지는 건드리지 않는다.
- [x] 여러 건 읽기 중 하나라도 없거나 권한이 없으면 어느 것도 읽음 처리되지 않는다. (위 6개: 2026-09-10 opencode 구현, 커밋 0f2d03d~f802d29. 테스트 102개와 claude의 실제 명령 검증으로 확인)
- [x] 같은 요청 키 재전송은 중복 메시지를 만들지 않고 다른 내용이면 거절된다.
- [x] 프로세스 종료 후에도 메시지와 수신 상태가 유지된다.
- [x] 저장 실패 시 메시지·수신 상태·중복 방지 기록이 일부만 남지 않는다.
- [x] `--body-file`로 전송한 긴 Markdown 본문이 원본 파일 변경 후에도 전송 당시 내용으로 조회된다.

- [x] 사용 가이드에 문서 폴더의 절대 경로·시작 문서·읽을 범위 예시와 본문 저장·경로 참조의 차이가 안내된다.
- [x] 전송·답장으로 수신자의 프로세스나 모델이 실행되지 않는다.
- [x] 실제 서로 다른 두 CLI 에이전트가 명시적 명령으로 요청 → 질문 → 답변 → 결과 전달을 수행한다. (2026-09-09, Claude Code와 OpenCode. 기록은 [05-agent-usage-guide.md](./05-agent-usage-guide.md) 10장)
