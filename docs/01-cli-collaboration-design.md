# twit CLI 기반 협업 기능 설계

> **대체됨 (2026-09-09)**: 이 문서는 v1 작업 관리 모델 설계다. [03-v2-mail-inbox-design.md](./03-v2-mail-inbox-design.md)와 [04-v2-implementation-design.md](./04-v2-implementation-design.md)가 대체했으며 구현하지 않는다.

- 작성일: 2026-09-09
- 상태: 초기 기능 설계. 명령과 데이터 구조는 구현 전 제안이다.
- 범위: 에이전트가 명시적으로 CLI를 호출하여 협업 기록을 조회하고 갱신하는 중계 시스템

## 1. 목적과 변경된 원칙

twit은 Codex, OpenCode, Grok 등 에이전트가 작업, 질문, 답변, 결과를 공유하는 저장소이자 CLI 인터페이스다. 기존 agent-bridge, oversee와 독립적으로 구성한다.

기존 Handoff의 실행기 폴링·배정 구독·CLI 자동 실행 구조는 이번 설계에서 제외한다. 에이전트 또는 사람이 필요한 시점에 `twit` 명령을 직접 실행한다.

1. 작업 조회, 인수, 질문, 답변, 제출, 검토는 모두 twit CLI를 통해 수행한다.
2. 폴링, 백그라운드 감시, 이벤트 구독, 예약 조회, 자동 재시도는 제공하지 않는다.
3. twit은 에이전트 CLI를 실행·종료·재개하거나 세션을 제어하지 않는다.
4. 작업 배정이나 답변 등록은 기록만 변경한다. 다른 에이전트를 깨우지 않는다.
5. 작업 수행은 이미 실행 중인 에이전트가 명시적으로 조회·인수한 이후에 이루어진다.
6. 에이전트 간 직접 메시지나 상대 CLI 호출 대신 twit에 협업 내용을 남긴다.
7. 프로세스 종료 여부를 작업 완료로 해석하지 않는다.

따라서 작업은 담당 에이전트가 다시 조회할 때까지 대기할 수 있다. 즉시 전달과 자동 진행은 보장하지 않는다. 사람이 에이전트를 시작하거나 기존 세션에서 조회를 요청하는 것은 twit 외부의 동작이다.

## 2. 구성

```text
사람 또는 실행 중인 에이전트
          │ 명시적 명령 호출
          ▼
       twit CLI
          │
          ▼
  작업 처리 계층 + 영속 저장소
```

| 구성요소 | 책임 |
|---|---|
| twit CLI | 입력 검증, 호출자 식별, 조회·변경 요청, 텍스트·JSON 출력 |
| 작업 처리 계층 | 권한 확인, 상태 전환 검증, 원자적 인수, 충돌 방지, 이력 기록 |
| 영속 저장소 | 참여자·작업·댓글·질문·제출·검토·변경 이력 보존 |
| 에이전트 또는 사람 | 명시적 조회, 실제 작업 수행, 검증, 기록 및 의사결정 |

초기에는 CLI가 로컬 저장소에 접근하는 구성을 제안한다. 서버 API와 여러 머신 지원은 별도 결정 사항이며, 어느 방식이든 자동 실행기는 두지 않는다.

## 3. 참여자와 자기 식별

`자기에게 할당된 작업`의 기준은 모델 이름이 아니라 등록된 참여자 ID다. 같은 CLI를 사용하는 여러 에이전트도 서로 다른 참여자로 구분할 수 있다.

```sh
twit actor list
twit whoami
```

- 참여자 필드: ID, 표시 이름, 종류(`human` 또는 `agent`), 참고용 CLI 종류, 활성 여부.
- 호출자 ID는 사전에 설정된 실행 환경의 프로필에서 가져온다.
- 호출자 설정이 없거나 등록되지 않은 ID라면 오류를 반환한다. 임의 담당자를 추정하지 않는다.
- 모델 종류는 실행 명령이나 권한을 결정하지 않는다.
- 초기 로컬 구성은 신뢰된 로컬 참여자를 전제로 한다. 프로필 ID는 보안 인증을 대신하지 않으며, 여러 머신·비신뢰 사용자 지원 시 인증과 권한을 별도 설계한다.

## 4. 현재 자기에게 할당된 전체 작업

```sh
twit task list --mine
twit task list --mine --status waiting_answer
twit task list --mine --role reviewer
twit task list --mine --include-closed --json
```

### 조회 규칙

- 기본 결과는 자신이 담당자 또는 검토자인 모든 미종료 작업이다.
- 완료·취소 작업은 기본 제외하며 `--include-closed`로 포함한다.
- 자신이 요청자이기만 한 작업은 기본 제외한다. `--role requester`로 명시적으로 조회한다.
- `--role assignee|reviewer|requester`, `--status`, `--parent` 필터를 제공한다.
- 여러 역할을 가진 작업은 한 번만 표시하고 모든 해당 역할을 표시한다.
- 갱신 시각 내림차순, 동일 시각이면 작업 ID순으로 정렬한다.
- 기본 명령은 조건에 맞는 전체 목록을 반환한다. 구현상 내부 페이지 처리가 필요해도 일부 결과를 전체인 것처럼 표시하지 않는다.
- 결과가 없으면 정상 종료하고 빈 목록을 반환한다.
- 조회는 담당자, 상태, 읽음 여부를 변경하지 않는다.

### 목록 출력

| 필드 | 내용 |
|---|---|
| ID·제목 | 작업 식별 및 요약 |
| 내 역할 | 담당자·검토자·요청자 |
| 상태 | 현재 작업 단계 |
| 담당자·검토자 | 현재 배정 |
| 응답 필요 | 자신에게 지정된 미답변 질문 수 |
| 내용 버전·리비전 | 요청 내용 버전과 동시 변경 검사용 번호 |
| 갱신 시각 | 마지막 변경 시각 |

전체 작업 목록은 짧은 요약만 제공한다. 상세 본문과 전체 댓글은 별도 조회하여 불필요한 문맥 전달을 줄인다.

## 5. 특정 작업 상세

```sh
twit task show T-001
twit task show T-001 --json
twit comment list T-001 --after C-010
twit history list T-001
```

상세에는 다음을 포함한다.

- 제목, 목적, 범위, 제약, 완료 조건, 참고 자료
- 요청자, 담당자, 검토자, 현재 상태
- 내용 버전, 리비전, 현재 작업 시도 ID
- 상위·관련 작업 및 차단 사유
- 미해결 질문, 현재 제출, 현재 제출에 대한 검토 결과
- 산출물 참조와 최근 댓글 20개
- 생성·갱신 시각

최근 댓글이 일부라면 전체 개수와 이전 기록 조회 방법을 명시한다. 원시 CLI 로그와 산출물 본문은 자동으로 펼치지 않는다. 파일 경로·커밋·URI 참조를 반환하며, 접근 불가 여부와 참조 존재 여부는 구분한다.

## 6. 작업 상태 변경

### 상태

| 상태 | 의미 |
|---|---|
| `draft` | 등록되었으나 아직 배정되지 않음 |
| `queued` | 담당자에게 배정되었으나 아직 인수되지 않음 |
| `in_progress` | 담당자가 명시적으로 인수하여 수행 중 |
| `waiting_answer` | 진행을 막는 질문의 답변 또는 확인 대기 |
| `blocked` | 환경·의존성 등의 문제로 진행 불가 |
| `in_review` | 결과를 제출하여 검토 대기 |
| `changes_requested` | 검토자가 수정을 요청함 |
| `done` | 제출 결과가 승인됨 |
| `cancelled` | 취소됨 |

### 명령과 전환 규칙

전용 명령이 필요한 전환은 일반 상태 변경 명령으로 우회하지 못한다.

| 명령 | 전환 | 호출자·조건 |
|---|---|---|
| `task assign` | `draft → queued` | 요청자가 활성 참여자를 담당자로 지정 |
| `task claim` | `queued/changes_requested → in_progress` | 현재 담당자가 원자적으로 인수, 새 시도 ID 발급 |
| `question ask --blocking` | `in_progress → waiting_answer` | 담당자가 수신자와 진행을 막는 질문을 등록 |
| `task resume` | `waiting_answer → in_progress` | 담당자가 모든 차단 질문의 해결을 확인 |
| `task status set … blocked` | `in_progress/waiting_answer → blocked` | 담당자가 사유와 필요한 조치를 기록 |
| `task resume` | `blocked → in_progress` | 담당자가 해소 근거 기록, 미해결 차단 질문이 없어야 함 |
| `task submit` | `in_progress → in_review` | 현재 담당자·시도가 현재 내용 버전의 결과와 검증 근거 제출 |
| `review approve` | `in_review → done` | 지정 검토자가 현재 제출 승인 |
| `review request-changes` | `in_review → changes_requested` | 지정 검토자가 묶음 수정 요청 기록, 현재 시도 종료 |
| `task cancel` | 미종료 상태 `→ cancelled` | 요청자가 사유 기록, 현재 시도 무효화 |
| `task reassign` | 배정된 미종료 상태 `→ queued` | 요청자가 새 담당자와 사유 기록, 현재 시도와 제출 무효화 |
| `task update` | 미종료 상태 `→ draft/queued` | 요청자가 요청 내용 변경, 배정 유무에 따라 상태 결정 |

검토자가 없는 작업은 요청자가 승인 또는 수정 요청을 수행한다. 제출만으로 자동 완료하지 않는다. 요청자와 담당자가 같으면 자기 승인 여부가 이력에 드러나도록 기록한다.

답변 등록은 자동 상태 변경이나 작업 재개를 일으키지 않는다. 담당자가 답변을 읽고 질문을 해결 처리한 뒤 `task resume`을 호출한다. `done`·`cancelled` 작업은 초기 버전에서 다시 열지 않고 후속 작업을 만든다.

```sh
twit task claim T-001 --expect-revision 3 --request-id req-claim-001
twit task status set T-001 blocked --reason "검증 DB 접근 불가" --expect-revision 4 --request-id req-block-001
twit task resume T-001 --reason "검증 DB 접근 복구 확인" --expect-revision 5 --request-id req-resume-001
```

## 7. 기타 필요한 기능

### 7.1 작업 등록·내용 변경·배정

```sh
twit task create --file task.json --request-id req-create-001
twit task assign T-001 --assignee opencode-1 --expect-revision 1 --request-id req-assign-001
```

- 등록 필수값: 제목, 목적, 작업 내용, 완료 조건. 요청자는 호출자로 기록한다.
- 선택값: 담당자, 검토자, 참고 자료, 상위 작업 ID, 관련 작업 ID.
- 담당자를 포함해 등록하면 `queued`, 생략하면 `draft`다.
- 새 하위 작업 등록도 동일한 경로를 사용한다. 하위 작업 생성·완료가 상위 작업 상태를 자동 변경하지 않는다.
- 요청 내용이나 완료 조건 변경은 내용 버전을 증가시킨다. 현재 시도와 제출을 무효화하고 담당자가 있으면 `queued`, 없으면 `draft`로 돌아간다.
- 검토자 변경은 요청자의 명시적 배정 변경으로 처리한다. 현재 제출이 있으면 이를 무효화하고 `queued`로 돌아가 재제출하게 한다.
- 담당자 변경, 요청 변경, 취소는 기존 에이전트 프로세스를 멈추지 않는다. 기존 담당자는 이후 CLI 호출에서 변경 사실을 확인할 수 있다.

### 7.2 진행 기록과 질문·답변

```sh
twit comment add T-001 --type progress --body-file milestone.md --expect-revision 6 --request-id req-progress-001
twit question ask T-001 --to codex-1 --blocking --body-file question.md --expect-revision 7 --request-id req-question-001
twit inbox list
```

- 댓글 유형: 진행 기록, 질문, 답변, 제출, 검토 결과, 시스템 기록.
- 제출·검토·시스템 기록은 전용 동작에서 생성하며 일반 댓글로 해당 동작을 대체할 수 없다.
- 질문은 수신자와 질문 ID를 가진다. 답변은 질문 ID에 연결한다.
- 질문 상태는 `open`, `answered`, `resolved`로 구분한다. 답변 등록 후 질문 작성자가 내용을 확인하고 해결 처리한다.
- `--blocking` 질문은 현재 담당자만 등록하며 작업을 `waiting_answer`로 전환한다. 대기 중에 추가 차단 질문을 등록할 수 있다.
- 일반 질문은 작업 상태를 변경하지 않는다.
- `inbox list`는 자신에게 온 미답변 질문과 자신이 작성한 질문의 미해결 답변을 조회한다. 담당 작업이 아닌 곳에서 받은 질문도 포함한다.
- 수신자 또는 요청자가 답변할 수 있고 실제 답변자를 기록한다.
- 진행 기록·질문·답변은 다른 에이전트 실행이나 푸시 알림을 유발하지 않는다.
- 과거 내용 버전의 질문·답변은 보존하되 현재 작업을 재개시키는 조건으로 사용하지 않는다.

### 7.3 제출·검토·산출물

제출에는 다음 필드를 요구한다.

| 필드 | 내용 |
|---|---|
| 내용 버전·시도 ID | 어떤 요청과 작업 시도에 대한 결과인지 |
| 결과 요약 | 수행 내용과 완료 조건 충족 여부 |
| 검증 근거 | 실행한 검증, 결과, 미실행 항목과 이유 |
| 산출물 참조 | 경로·URI·커밋 등 결과를 확인할 위치 |
| 남은 문제 | 제한, 미해결 사항, 후속 작업 |

- 제출마다 고유 제출 ID를 부여한다. 검토는 해당 제출 ID에 연결한다.
- 변경 가능한 파일 경로만 제공하기보다 커밋 ID나 고정된 산출물 위치를 권장한다.
- 오래된 내용 버전·시도의 결과는 과거 제출로 보존하되 현재 제출이나 상태를 변경하지 않는다. CLI는 미채택 사실을 명시한다.
- 검토자는 승인 또는 하나로 정리한 수정 요청을 기록한다.
- 수정 후에는 새 시도로 인수하고 새 제출을 등록한다. 이전 제출과 검토는 보존한다.
- twit은 CLI를 실행하지 않으므로 원시 로그를 자동 수집하지 않는다. 수행자가 필요한 로그를 보관하고 참조를 제출한다.

### 7.4 수동 복구와 작업 시도

실행기·프로세스를 추적하는 실행 ID 대신 협업 기록용 `attempt_id`를 사용한다. 이는 CLI 세션 ID나 OS 프로세스 ID가 아니다.

- 인수 시 시도 ID를 생성하고 담당자와 연결한다.
- 시도에는 시작·제출·수정 요청·무효화 등의 이력을 남긴다.
- 하트비트나 소유권 자동 만료는 없다. 시간이 지나도 자동 재배정하지 않는다.
- 에이전트 종료·연결 단절을 twit이 감지하지 않는다. 작업이 오래 진행 중이면 사람이 상세와 이력을 확인하고 요청자 권한으로 명시적으로 재배정하거나 취소한다.
- 같은 담당자로 재배정하여 재시도할 수 있으며 사유를 요구한다.
- 재배정 이후 과거 담당자의 실제 파일 수정까지 차단하지는 못한다. 코드 작업은 별도 디렉터리 또는 worktree를 기본으로 사용한다.

### 7.5 일관성과 CLI 출력 계약

- 모든 변경은 작업 변경과 이력 기록을 하나의 트랜잭션으로 저장한다.
- `content_version`은 요청 내용·완료 조건 변경을 식별한다.
- `revision`은 댓글·배정·상태 등 작업에 연결된 모든 변경마다 증가한다.
- 기존 작업 변경 명령에는 `--expect-revision`을 요구한다. 충돌하면 변경하지 않고 최신 상세 재조회를 안내한다.
- 모든 변경 요청은 `--request-id`를 받는다. 동일 호출자의 같은 요청 ID·같은 입력 재전송에는 기존 결과를 반환하며, 같은 요청 ID에 다른 입력이면 오류다.
- 인수는 배정·상태·리비전을 원자적으로 확인한다. 서로 다른 인수 요청이 동시에 오면 하나만 성공한다.
- 상태 전환에는 현재 담당자·시도·내용 버전을 검증한다. 권한 확인은 CLI 표시뿐 아니라 작업 처리 계층에서 수행한다.
- 사람용 텍스트와 에이전트용 `--json`을 제공한다. JSON 출력에는 `schema_version`, `ok`, `data`, `error`를 포함한다.
- 오류 코드는 최소 `NOT_FOUND`, `ACTOR_NOT_CONFIGURED`, `FORBIDDEN`, `REVISION_CONFLICT`, `INVALID_TRANSITION`, `STALE_ATTEMPT`, `VALIDATION_ERROR`를 구분한다.
- 성공은 종료 코드 0, 오류는 비영 종료 코드로 구분한다. 과거 제출 보존은 성공 응답의 `accepted_as_current: false`로 현재 결과 미채택을 명시한다.
- JSON은 표준 출력, 진단 메시지는 표준 오류로 분리한다. 원시 로그나 비밀값을 임의로 출력하지 않는다.

## 9. 기본 사용 흐름

1. 요청자가 작업과 완료 조건을 등록하고 담당자를 지정한다.
2. 담당 에이전트가 `task list --mine`을 호출한다.
3. `task show`로 내용을 읽고 `task claim`으로 인수한다.
4. 작업을 수행하고 필요한 시점에 진행 기록을 남긴다.
5. 판단이 필요하면 질문을 등록한다. 답변자는 직접 `inbox list`를 조회하여 답변한다.
6. 담당자는 다음 명시적 조회에서 답변을 확인하고 질문 해결·작업 재개 명령을 호출한다.
7. 담당자가 결과와 검증 근거를 제출한다.
8. 검토자가 자신의 목록과 제출을 직접 조회하고 승인하거나 수정을 요청한다.
9. 수정 요청이 있으면 담당자가 다음 조회에서 확인하고 다시 인수한다.

어느 단계도 다음 참여자의 실행을 자동으로 유발하지 않는다.

## 10. 초기 범위 및 후속 결정

초기 포함:

- 참여자 식별, 자신의 전체 미종료 작업 조회, 작업 상세
- 등록·배정·인수·상태 변경·취소·수동 재배정
- 유형별 기록, 질문·답변·수신함
- 제출·검토·산출물 참조
- 영속 저장, 동시 변경 감지, 중복 요청 처리, 오래된 결과 미채택
- 텍스트·JSON 출력

초기 제외:

- 실행기, 폴링, 이벤트 구독, 자동 알림·깨우기
- 에이전트 CLI 실행·세션 재개·프로세스 감시
- 자동 재시도·재배정·모델 선택
- 웹 칸반 UI, 공유 파일 동시 수정, 원시 로그 자동 수집
- 기존 스킬 개편

구현 전에 결정할 사항:

- 구현 언어와 CLI 배포 방식
- 로컬 DB 종류 및 저장 위치·초기화 방식
- 참여자 등록과 프로필 설정 명령
- 산출물 경로 기준 및 보존 정책
- 서버·여러 머신 지원 여부와 해당 환경의 인증

## 11. 검증 및 완료 조건

- [ ] 참여자별 목록에 담당·검토 역할의 모든 미종료 작업이 중복 없이 표시된다.
- [ ] 완료·취소 작업 포함 옵션과 빈 목록이 정확하게 동작한다.
- [ ] 작업 상세에서 완료 조건, 현재 제출, 질문, 과거 기록을 확인할 수 있다.
- [ ] 배정·댓글·질문·답변만으로 다른 프로세스나 모델이 실행되지 않는다.
- [ ] 질문 수신자가 담당자가 아니어도 수신함에서 질문을 찾는다.
- [ ] 답변 등록 후 담당자의 명시적 해결·재개 전에는 대기 상태가 유지된다.
- [ ] 미해결 차단 질문이 남아 있으면 재개할 수 없다.
- [ ] 동시 인수 요청 중 하나만 성공하고, 동일 요청 재전송은 중복 기록을 만들지 않는다.
- [ ] 잘못된 권한·상태 전환·오래된 리비전 요청은 변경 없이 거절된다.
- [ ] 취소·재배정·내용 변경 이후 제출된 과거 결과가 현재 상태를 덮어쓰지 않는다.
- [ ] 검토가 특정 제출에 연결되며, 검토자가 없으면 요청자가 승인한다.
- [ ] CLI 프로세스가 종료되어도 다음 호출에서 저장된 작업과 이력을 조회할 수 있다.
- [ ] 서로 다른 두 CLI 에이전트가 직접 호출 없이 twit 명령만으로 등록·조회·인수·제출·검토를 수행한다.

실제 CLI 연동과 사용량 절감은 구현 이후 검증한다. 이 문서는 기능 설계이며 구현 완료를 의미하지 않는다.
